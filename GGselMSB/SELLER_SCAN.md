## Что узнали про API пагинацию

### Проблема — API зациклен
Все каталожные эндпоинты (`rec-goods`, `categories`) при `page > 1` возвращают **те же товары что на странице 1**. Реального смещения нет.

```
GET /elastic/goods/rec-goods page=1   → [id1, id2, id3...]
GET /elastic/goods/rec-goods page=200 → [id1, id2, id3...]  ← одинаково!
```

### Лимит `/elastic/goods/categories`
- Принимает только `sort=sortByRec`
- Реально отдаёт максимум ~10 000 уникальных товаров на content_type_id
- Страница 201+ → пустой ответ

### Фильтр по продавцу не работает
```python
POST /elastic/goods/categories {"id_seller": 998188}
# Возвращает глобальный каталог, игнорирует фильтр
```

## Что реально работает

| Метод | Уникальных товаров | Статус |
|-------|-------------------|--------|
| `full_scan` по content_type_id | ~10k на категорию × 19 = ~105k | ✅ Сделано |

| Фильтр по продавцу через API | Не работает | ❌ |

## Варианты добора оставшихся ~280k товаров

### Вариант A — Парсинг страниц продавцов (HTML)
Каждый продавец имеет страницу: `ggsel.net/sellers/{id}`
На ней видны ВСЕ его товары через "Показать ещё" (JS/fetch).

**Эндпоинт который браузер использует:**
Нужно перехватить через DevTools при нажатии "Показать ещё" на странице продавца.

**Шаги:**
1. Открыть `ggsel.net/sellers/998188` в браузере
2. DevTools → Network → нажать "Показать ещё"
3. Найти XHR запрос — это и есть реальный эндпоинт
4. Реализовать в `run_seller_scan.py`

**Плюсы:** Покрывает ВСЕ товары каждого продавца
**Минусы:** Нужна разведка эндпоинта

### Вариант B — back-office.ggsel.com
Seller-API может иметь отдельный эндпоинт для листинга товаров продавца.
Требует токен продавца (не покупателя).

### Вариант C — Поиск по seller_name через query_string
```python
POST /elastic/goods/categories {
    "query_string": "GalaxyLink",  # имя продавца
    "content_type_ids": []
}
```
Может возвращать товары конкретного продавца если имя уникальное.
