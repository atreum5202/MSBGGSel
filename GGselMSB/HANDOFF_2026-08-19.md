## 2. Архитектура категорий ggsel.net (как устроено)

**Три разных ID-пространства**, и они НЕ равны друг другу:

| Пространство | Что это | Где встречается | Пример (Roblox) |
|---|---|---|---|
| **`ggsel_digi_catalog`** | ID категории на витрине ggsel.net (URL `/catalog/<id>`) | Везде в БД GGselMSB (`seller_categories.id`, `category_slug_mapping.seller_id`) | **28144** |
| **Live seller API id** | Внутренний id в `seller.ggsel.com` | Ответы `/api/v1/categories*` | другое число (например 30508) |
| **Slug** | URL-friendly имя | URL `ggsel.net/catalog/<slug>`, `category_slug_mapping.slug` | `roblox` |

**Важный вывод**: в БД `seller_categories.id` и `category_slug_mapping.seller_id` хранят `ggsel_digi_catalog`, **НЕ** live seller API id. Название поля `seller_id` в `category_slug_mapping` — **вводит в заблуждение**, на самом деле это `ggsel_digi_catalog`. Если кто-то будет менять код, это критично.

**Live API endpoints** (проверены живьём через MSB профиль 95):

| Метод | URL | Что отдаёт |
|---|---|---|
| GET | `https://seller.ggsel.com/api/v1/categories` | 6 корневых категорий |
| GET | `https://seller.ggsel.com/api/v1/categories?parent_id=X&limit=100&page=1` | **Прямые дети X** (пустой = лист) |
| GET | `https://seller.ggsel.com/api/v1/categories/{id}/tree` | **ВСЮ цепочку от корня до {id}** (с `ancestor_ids` у каждого) |
| GET | `https://seller.ggsel.com/api/v1/categories/{id}` | 404 |
| GET | `https://seller.ggsel.com/api/v1/categories/{id}/children` | 404 |
| GET | `https://api.ggsel.com/elastic/goods/categories` | листинг товаров (для парсинга) |

**Главный путь обхода дерева** (рекурсия снизу вверх + parent_id):
- `GET /api/v1/categories` → 6 корней
- `GET /api/v1/categories?parent_id=X` → дети X
- `GET /api/v1/categories/{leaf}/tree` → путь от листа до корня

## 5. Что починили (5 точек)

### 5.1 Создали `parser/category_resolver.py` (~190 строк)
**Заменяет потерянный `map_categories.py`.**

API:
- `find_seller_category_id(slug_or_id, db_path=None, min_score=0.7)` → int | None
- `get_by_seller_id(seller_id, db_path=None)` → dict | None
- `resolve_with_tree(slug_or_id, db_path=None)` → dict | None (с `seller_tree`)

Логика `find_seller_category_id`:
1. Если int/str-int → passthrough
2. Иначе: `SELECT seller_id FROM category_slug_mapping WHERE slug=? AND match_score >= ? ORDER BY match_score DESC, LENGTH(seller_tree) ASC LIMIT 1`
3. Fallback: substring match по `seller_title`
4. None если не нашли

Логика `get_by_seller_id`:
1. Сначала в `category_slug_mapping`
2. Fallback в `seller_categories` (с полным деревом из `ancestor_ids`, `ggsel_digi_catalog`, `unit`, `text_for_sellers`)

### 5.2 Поправили `parser/ggsel_publisher.py`

## 10. Ключевые технические решения

### 10.1 ID в БД = `ggsel_digi_catalog`
**КРИТИЧНО**: В `seller_categories.id` и `category_slug_mapping.seller_id` хранится `ggsel_digi_catalog`, **НЕ** live seller API id. При размещении оффера через `POST /api_sellers/v2/offers` нужно слать это число как `category_id`.

### 10.2 Live seller id доступен через `/api/v1/categories/{id}/tree`
Для размещения оффера 102388481 (Google Drive 5TB + Gemini Pro):
```
GET /api/v1/categories/39082/tree →
[
  {id: 27, ggsel_digi_catalog: 33749, title: "Сервисы и соцсети"},
  {id: 5855, ggsel_digi_catalog: 42813, title: "Google Drive (Гугл Диск)"},
  {id: 39081, ggsel_digi_catalog: 129444, title: "Google Drive"},
  {id: 39082, ggsel_digi_catalog: 129445, title: "Услуги активации"}  ← placement
]
```
Здесь `id` = live seller id, `ggsel_digi_catalog` = ggsel витрина id. **В БД GGselMSB — `id` ссылается на `ggsel_digi_catalog`**, не на live seller id. Это разные пространства!

### 10.3 `category_slug_mapping.seller_id` — это `ggsel_digi_catalog`
Название поля вводит в заблуждение. Реальное содержимое:
- `seller_id=28144, slug='roblox', title='Roblox', match_score=0.95`
- НЕ live seller id, а `ggsel_digi_catalog=28144` (что равно live seller id для Roblox — **совпадение**)

### 10.4 Аутентификация seller API
- **Кабинет (UI)**: `ACCESS_TOKEN` JWT в cookie
- **Прямой API** (`/api_sellers/v2/offers`): `GGSEL_API_KEY` в `Authorization: Bearer XXX`
- Опционально: `GGSEL_API_AUTH_SCHEME=""` если API ждёт raw-ключ

### 10.5 Структура дерева
- 6 корней (depth=0), 420 depth=1, 1286 depth=2, 1535 depth=3, 495 depth=4
- Всего 4776 узлов в `seller_categories` (после refresh — 9187, т.к. добавились новые)

**Типичные проблемы и решения**:
| Проблема | Решение |
|---|---|
| `WebSocket 404` при прямом подключении к `ws://127.0.0.1:PORT` | Использовать `playwright.chromium.connect_over_cdp("http://127.0.0.1:PORT")` вместо сырого WS |
| `Execution context was destroyed` (страница навигирует) | Использовать `ctx.new_page()` (новая вкладка) вместо `ctx.pages[0]`, и **не вызывать** `wait_for_load_state("networkidle")` (ggsel постоянно грузит RSC prefetch + Yandex Metrika) |
| `networkidle` timeout | Убрать; использовать `domcontentloaded` + `wait_for_timeout(2-4s)` |
| `429 Too Many Requests` от seller API | BATCH=3, `await asyncio.sleep(0.4)` между батчами |
| 2xx OK но `data=[]` в ответе | Неправильный query param или `parent_id` не передан в JS-функцию — Playwright требует `page.evaluate(expr, arg)` где arg = одно значение, не IIFE `((pid) => { ... })()` |
| Прокси залочил | Сменить через PATCH, рестарт профиля |
| `ERR_FAILED` на `https://ggsel.net/catalog/<slug>` | Qrator/Cloudflare блок. Ждать и retry, или пропускать slug |
| Открыто слишком много вкладок после BFS | Cleanup-скрипт: `python _cleanup_tabs.py` (закрывает всё кроме seller.ggsel.com) |

**Cleanup после BFS** (если в профиле накопилось 10+ вкладок):
```python
# GGselMSB/_cleanup_tabs.py
import asyncio
from playwright.async_api import async_playwright

async def main():
    async with async_playwright() as p:
        b = await p.chromium.connect_over_cdp("http://127.0.0.1:56417")
        for c in b.contexts:
            for pg in list(c.pages):
                if "seller.ggsel.com" in pg.url:
                    continue
                await pg.close()
        await b.close()
asyncio.run(main())
```
